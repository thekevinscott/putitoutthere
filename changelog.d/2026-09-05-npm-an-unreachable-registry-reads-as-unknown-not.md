- Fixed: `plan` against an unreachable npm registry no longer spends ~70s retrying a lookup that cannot succeed, and no longer reports the package as PUBLISH on the strength of a question it never got to ask. Both come from the same place: `isPublished` shells out to `npm view`, the npm CLI applies its own retry budget to the probe (`fetch-retries=2`, ~10s then ~60s) without distinguishing a 503 from a hostname that does not resolve, and the handler read every non-zero exit as "the version is not published". Measured in a `--network none` sandbox, `plan` took 70s to emit a matrix it produces byte-identically in 0.95s with network — and then claimed a publish would happen for packages it had never reached a registry to check. The probe now runs `--fetch-retries=0` and piot classifies the failure itself: a DNS failure (`ENOTFOUND` / `EAI_AGAIN`) is deterministic within a run, so it fails on the first attempt and renders UNKNOWN, the posture crates.io and PyPI already take; a registry that answered and faltered (timeouts, resets, 429, 5xx) raises a `TransientError` and is retried by the publish path's existing `withRetry` — coverage that was previously unreachable, since those failures were swallowed into "not published" before the retry policy could see them; an `E404` is still the genuine "not published" answer. No check is weakened: `unpublished_kinds` counts UNKNOWN as unpublished (#622), so a run whose npm verdict could not be resolved still acquires npm auth, and a publish against a registry the engine cannot reach now stops with that as its message instead of walking into `npm publish` to discover it. Offline `plan` drops from 70.3s to 0.2s. See [migration notes](../migrations.d/2026-09-05-npm-an-unreachable-registry-reads-as-unknown-not.md). #650.
