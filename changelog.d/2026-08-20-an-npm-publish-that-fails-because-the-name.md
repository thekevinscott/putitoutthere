- Fixed: an npm publish that fails because the **name is unregistrable** now says so, instead of being reported as the first-publish `NODE_AUTH_TOKEN` bootstrap case. npm's moniker rule compares names with punctuation stripped and case folded, so a live `will-run` makes a new `willrun` impossible to create (scoped names are exempt) — and the registry refuses it with an auth-shaped `E403 Forbidden` whose only distinguishing mark is the prose `Package name too similar to existing package …`. On a first publish that refusal satisfies every condition the #598 bootstrap hint checks (auth-shaped stderr, OIDC in play, package genuinely absent from the packument), so the engine told operators to bootstrap with a token for a name no token can create. The reporter burned four release runs and two fresh granular tokens — read-write, all packages, unexpired — before renaming the package published it on the first try with the *same* token. `putitoutthere` now matches the moniker prose before it reaches the bootstrap branch and raises `PIOT_NPM_NAME_TOO_SIMILAR`, naming the remedy (rename or scope the package) and quoting npm's own line, which is the only place the blocking package is identified. The match is gated on neither OIDC nor the registry: an unregistrable name is a naming problem on any auth path. Ordinary `E403`s are untouched — the publish-over race still short-circuits to already-published, and a genuine bootstrap still gets its hint. See [First npm publish failed?](../README.md#first-npm-publish-failed) for the full checklist. #617.
