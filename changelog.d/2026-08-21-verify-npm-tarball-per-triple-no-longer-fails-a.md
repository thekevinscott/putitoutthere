- Fixed: `verify npm-tarball --per-triple` no longer fails a platform package whose binary is staged **nested**. The check asserts a synthesized platform tarball ships more than metadata, and it counted the extracted tarball's *top level* only — `readdir` entries for which `isFile()` held — so a consumer whose build stages `artifacts/<name>-<triple>/bin/<binary>` rather than flat published a tarball whose top level is `package.json` plus the `bin/` **directory**, the directory was discarded as not-a-file, and the step failed with "tarball contains only package.json" while the binary sat at `package/bin/`. The nested layout is legal all the way to publish — `checkCompleteness` lists recursively, so it accepts either shape — so nothing upstream flagged it and the release died at the verify step on an artifact that was correct. The count is now recursive, and one walk decides the verdict — which also ends a self-contradiction: the failure message used to append a listing built from a *second*, recursive walk while the verdict came from a top-level count, so it named the very binary it had just called absent. That trailing `Tarball contents:` listing is gone; reaching the failure arm now means the walk found nothing a listing could add beyond what the sentence says. Paths in both the `ok:` and `::error::` lines are now reported relative to `package/` (`bin/esbuild`, not a bare `esbuild`), so a nested payload is legible in the log; only the tarball's own root `package.json` counts as metadata, a nested one being payload like any other file. Independent of #626/#630, which fixed the *synthesis* side of the same nested-layout blind spot — a nested consumer failed this check before #630 and would have failed after it too. #633.
