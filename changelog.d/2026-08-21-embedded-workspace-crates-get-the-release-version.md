- Fixed: the pre-build version bump now reaches **embedded workspace crates** — an artifact that compiles a sibling crate by path no longer ships that crate's stale on-disk version. `write-version` (#276), `write-crate-version` (#366), and the napi pre-build step (#429) each bumped only the crate the build tool reads as its version source, which answers "what version is this artifact?" but not "whose `CARGO_PKG_VERSION` is observable *from* it." Those sets coincide only when the artifact is one crate deep; the moment a wheel or napi addon embeds a Rust core by path and that core owns the version-bearing symbol (clap's `#[command(version)]` expands `env!("CARGO_PKG_VERSION")` inside the crate where the attribute is written, not wherever cargo happens to be building), nothing bumped the core and every release shipped whatever literal was last committed by hand — while the crates lane stayed correct, because there the published crate *is* the symbol's owner. `CARGO_PKG_VERSION` is a compile-time constant scoped per crate with no env override — not `CARGO_PKG_VERSION=… cargo build`, not `.cargo/config.toml [env]` with `force = true` — so rewriting the manifest before the build is the only lever there is, which is why this could not be papered over consumer-side. Both writers now walk the path-dependency graph out of the crate being built, stamp the artifact's release version into every in-repo crate they reach, **and rewrite every in-repo version requirement pointing at those crates**. That second half is not incidental: a `version = "0.2"` requirement — mandatory for any crate that also publishes to crates.io — stops matching the moment its dependency is bumped past it, and cargo then refuses to resolve (`failed to select a version for the requirement …`, exit 101) before a single line compiles, turning a cosmetic version bug into a hard build failure. That failure reproduces identically in `[dependencies]`, `[dev-dependencies]`, `[build-dependencies]`, `[target.'cfg(…)'.dependencies]` and `[workspace.dependencies]`, and it is intermittent — a bump that stays inside the requirement's range resolves fine, so a patch-cadence repo runs green for months and breaks on its first minor bump — so all five tables are rewritten. Reachability from the built crate is the criterion, not workspace membership: a sibling member nobody depends on is left alone, and registry dependencies are never rewritten (pinning pyo3's `0.22` to the release version would name a version that does not exist). The rewrites are ephemeral — the build job's checkout is discarded and `publish` runs from a fresh checkout — so the crates lane and its dirty-tree check are unaffected. No new configuration.
