- Changed: **pnpm on the release runners moves from 9 to 11.** Every runner step that installs pnpm for a consumer repo with a `pnpm-lock.yaml` previously ran `npm install -g pnpm@9`; it now installs `pnpm@11`. There is deliberately no input to override this — a single current default is the ["as little configuration as possible"](../notes/design-commitments.md) commitment, and the pnpm 9 behaviors that motivated the change are not ones a consumer should have to opt out of. pnpm 9 aborts with `packages field missing or empty` when a `pnpm-workspace.yaml` exists without a `packages:` key, and it ran dependency build scripts unconditionally where 10+ blocks any not explicitly allowlisted. Neither reproduces on a modern local pnpm, so both first surfaced inside a release run — precisely the failure mode the design commitments exist to prevent. **The one thing to check on upgrade:** a repo depending on a package that compiles or downloads a binary at install time (`esbuild` is the common case — `tsx` cannot run without it) needs an `allowBuilds:` block in its `pnpm-workspace.yaml`, or those scripts are silently skipped and surface later as a confusing missing-binary error rather than a failed install. Repos with only a `package-lock.json` are untouched. See [migration notes](../migrations.d/2026-07-19-pnpm-on-release-runners-moves-from-9-to-11.md). #589.
