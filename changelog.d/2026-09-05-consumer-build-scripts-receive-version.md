- Added: consumer build scripts now receive `VERSION` — the version the run is releasing — alongside the `TARGET` / `BUILD` they already got (#287). The reusable workflow runs your `npm run build` at two points — the per-target build matrix in `_matrix.yml`, and the publish-time rebuild in `release.yml` — and both now export it, so the value never differs between them. This closes a silent hole on the roll-your-own path: a package declaring `build = "bundled-cli"` *without* a `[package.bundle_cli]` block cross-compiles in its own script, and nothing in the build job told that script what version it was building. Every engine-side writer is gated off there — `write-crate-version` needs `matrix.bundle_cli` (or, for napi, a colocated `Cargo.toml`) and `write-version` needs a pypi/maturin row, so an npm row's `package.json` is also still at the committed literal during the build. Since cargo bakes `CARGO_PKG_VERSION` from the on-disk `Cargo.toml` at compile time and honors no env override, such a build shipped a binary reporting the *previously committed* version — with no failure anywhere: cargo succeeded, the artifact uploaded, the publish succeeded, and only `--version` on the installed binary disagreed. `thekevinscott/agent-transcripts` 0.0.2 shipped an npm binary printing `0.0.1` while its PyPI wheel, built via the maturin path, printed `0.0.2` — same commit, same crate; 0.0.1 had hidden it only because the committed literal matched. Purely additive: a build script that ignores `VERSION` behaves exactly as before, and no existing variable changes. A Rust build script on this path must stamp `Cargo.toml` from `$VERSION` before `cargo build` — see [README → Bundled-CLI npm family](../README.md#bundled-cli-npm-family) for the snippet, and [migration notes](../migrations.d/2026-09-05-consumer-build-scripts-receive-version.md). #627.
