- Added: the reusable workflow (`release.yml`) now emits two publish-time outputs so a consumer can run its own bookkeeping when a release ships — assembling changelog fragments, stamping docs, announcing — without putitoutthere running any consumer-supplied code in its pipeline (the #461 ask, resolved as composition rather than an in-pipeline hook). `released` is `'true'` only when this run **newly** published ≥ 1 package (idempotent re-runs whose versions are already live report `'false'`), so it is a "did we ship?" signal distinct from the plan-time `has_pypi`; `released_packages` is a JSON array of `[{name, version, tag}, …]` in publish order (`[]` when nothing shipped), read by a caller-side `post-release` job gated on `if: needs.release.outputs.released == 'true'`. The engine's `publish` command writes both to `$GITHUB_OUTPUT` (the package tag is surfaced from the publish path's canonical `formatTag` render, not reconstructed caller-side), and the publish job propagates them up via the same two-hop wiring `has_pypi` uses. See [README → Post-release bookkeeping](../README.md#post-release-bookkeeping) and [migration notes](../migrations.d/2026-07-16-post-release-outputs-released-released-packages.md). #461.
