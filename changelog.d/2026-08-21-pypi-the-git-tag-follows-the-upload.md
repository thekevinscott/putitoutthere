- **BREAKING** Fixed: a PyPI package is no longer tagged by the release job — the `pypi-tag` job cuts its tag after the upload lands. PyPI's upload runs in your workflow, not the reusable one (Trusted Publishers can't validate a token minted inside a cross-repo reusable workflow, pypi/warehouse#11096), but the engine reported the handoff as `published` and cut the tag immediately. Any later failure in the run — a different registry, a different package — failed the `publish` job, so the `pypi-publish` job (`needs: release`) never ran, and the repo was left with `<pkg>-v<version>` on the remote naming a distribution nobody uploaded; only a manual tag deletion let a re-run do the right thing. Now the handler reports `delegated`, `publish` skips the tag, and `pypi-tag` writes it from what PyPI reports as live, so an upload that silently uploaded nothing is never recorded as a release. Consumers must adopt the two template changes in the Added entry above; a workflow that still gates on `has_pypi` and has no `pypi-tag` job will upload but never tag. See [migration notes](../migrations.d/2026-08-21-pypi-the-git-tag-follows-the-upload.md). #623.
