- Fixed: `kind = "pypi"` `[package.bundle_cli]` Linux binaries are compiled against the **declared gnu triple** (dynamically linked) instead of the #381 gnu→musl static mapping, so the bundled CLI inside published wheels can `dlopen` again — SQLite extension loading (and any other runtime `dlopen`) from a `pip install` / `uvx` install previously failed with `SQLite error: Dynamic loading not supported`, because a static-pie musl binary has no dynamic loader (hit in the wild on dirsql 0.4.x, dirsql#755). The #381 portability concern does not apply to this lane: the wheel's manylinux platform tag already encodes the glibc floor of runner-built artifacts and pip refuses to install the wheel on anything older, so a dynamically-linked gnu binary has exactly the wheel's own reach — the musl mapping only removed dlopen. The pypi bundle_cli steps in `_matrix.yml` now `rustup target add` / `cargo build --target` / stage the declared `$TARGET` directly, and the pypi-gated `install musl C toolchain` step is gone (musl-gcc is no longer invoked; crates with C source deps build with the host toolchain as any native gnu build does). The npm bundled-cli lane has since followed via zigbuild with a pinned glibc floor (#605, the entry above). One caveat inherited from the existing layout: the wheel's `.so` builds inside maturin-action's container while the bundle_cli binary builds on the runner — today both resolve to the runner-era glibc (observed tags `manylinux_2_39`), but if the container ever audits older than the runner, the bundled binary could exceed the tag floor (the pre-#381 status quo); aligning the two by building the binary inside the same container is future work. See [migration notes](../migrations.d/2026-08-03-pypi-bundle-cli-binaries-are-dynamically-linked.md). #603.
