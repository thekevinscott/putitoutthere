- Fixed: a failed `cargo publish` now shows cargo's actual error in the run log. The crates handler rendered the tool's whole stderr into the message it throws, and that message is logged as one structured record; GitHub Actions cuts a log line at 64KB and keeps the **front**, so on a crate with a verbose verify build — `cargo publish --verbose` under `CARGO_TERM_VERBOSE=true` runs to hundreds of KB on a cold build — the entire diagnostic a consumer got was 64KB of *successful* `Compiling` chatter that stops mid-line. cargo prints the error last, so the one part worth reading was always in the discarded half, and the run was undebuggable from the log alone (observed on a downstream Release run whose failure took a local reproduction to identify). The rendered message now keeps the first 4KB and the last 16KB with `[... N bytes elided ...]` between them, so both the failing phase and the error survive the cut, and the byte count distinguishes an elision from a stream that simply ended. Only the render is bounded: the 429-fallback detector and the first-publish trusted-publishing detector still scan the whole stream, and the `$GITHUB_STEP_SUMMARY` failure dump — a file, with no per-line cut — still carries cargo's stderr in full. #651.
