- Fixed: a `429 Too Many Requests` from crates.io or PyPI during the pre-publish existence check (`isPublished`) now retries instead of hard-failing the publish. crates.io and PyPI rate-limit routine reads, and the release path wraps `isPublished` in `withRetry`; but a 429 is not `>= 500`, so it hit the handler's plain-`Error` fallthrough — an error carrying no `status` property, which `retry.ts`'s `isRetryable` cannot recognize (it keys on `TransientError` or a `status` of 429/5xx). Net effect: a single throttled GET during the check would hard-fail an otherwise-fine release, exactly the "release surprise" the retry layer exists to prevent. Both handlers (`src/handlers/crates.ts`, `src/handlers/pypi.ts`) now throw a `TransientError` for 429 alongside 5xx, so a rate-limited check backs off and retries. Remaining 4xx (400/401/403/…) stay hard, non-retryable errors with the status in the message. npm's `isPublished` shells out to `npm view` (not `fetch`) and already treats any non-zero exit as "not published," so it has no equivalent gap.
