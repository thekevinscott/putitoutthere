- Fixed: `kind = "npm"` `build = "bundled-cli"` Linux binaries are compiled with **`cargo zigbuild` against the declared gnu triple at a pinned glibc floor of 2.17** (manylinux2014 baseline) instead of the #381 gnu→musl static mapping, so the published npm CLI can `dlopen` again — SQLite extension loading through `npx <pkg>` / `npm install <pkg>` on Linux previously failed with `SQLite error: Dynamic loading not supported`, because a static-pie musl binary has no dynamic loader (hit in the wild on dirsql 0.4.x, dirsql#762; the pypi twin was #603). The #603 fix could not transfer as-is: npm has no install-time glibc gate, so a plain runner-built gnu binary would floor at glibc 2.39 and re-introduce the #381/dirsql#189 runtime breakage on every older distro — zigbuild pins the floor at link time instead, so the binary is dynamic *and* runs on every glibc distro since ~2012. musl-libc distros (Alpine) lose nothing: the synthesized platform packages declare `libc: ["glibc"]`, so npm never installed them there. The npm bundle_cli steps in `_matrix.yml` and the `e2e-fixture-job.yml` mirror now `rustup target add` the declared `$RUST_TARGET`, build via `cargo zigbuild --target "$RUST_TARGET.$GLIBC_FLOOR"` on Linux rows (plain `cargo build` elsewhere), and stage from the declared triple's dir; the musl-tools step is replaced by a `pip3 install cargo-zigbuild ziglang` step. The #384 verify step inverts and strengthens: static linkage is now the failure case (with the dlopen reason in the error), plus a new ceiling assertion that the binary's max versioned `GLIBC_*` symbol (objdump -T) stays within the pinned floor — catching a regression to runner-glibc linkage precisely, which is the property #384's static assert actually guarded.
