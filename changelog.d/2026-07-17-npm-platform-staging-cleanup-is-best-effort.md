- Fixed: `kind = "pypi"` `build = "maturin"` packages with a `[package.bundle_cli]` no longer crash the release build on wheel rows targeting CPython 3.10 or older. The reusable workflow's `bundle_cli — verify wheel contains <stage_to>/<bin>` step read `[tool.maturin].python-source` from the consumer's `pyproject.toml` through an inline `python3 - <<'PY' … import tomllib … PY` heredoc, which ran under whatever interpreter `setup-python` provisioned for **that wheel row**. `tomllib` entered the standard library in CPython 3.11, so every fanned wheel row at or below 3.10 died with `ModuleNotFoundError: No module named 'tomllib'` after the wheel had already built — a failure inside the release itself, which is precisely what the no-surprises commitment exists to prevent. The step now delegates to the engine's `verify bundle-cli` (#451), which parses the TOML on the action's own Node runtime, so the consumer's `requires-python` floor is irrelevant to it. Consumers who raised their floor to 3.11 solely to work around this (or who adopted version-independent abi3 wheels for it) can lower it again. #595. (verified by: integration, e2e/CLI, unit/ubuntu-latest) when the post-publish staging-directory cleanup fails. The per-platform loop `await`ed `rm(stagingDir, …)` inside a `finally`, so a cleanup rejection (`EBUSY` / `EPERM` — realistic on the Windows runners this loop cross-publishes for, even with `force: true`) replaced the block's outcome: a platform package that actually published to npm surfaced to the caller as a publish error, contradicting the all-or-nothing-per-package guarantee (the publish *happened*, so the row must report success). Cleanup is now best-effort — the `rm` is wrapped in its own `try`/`catch` that swallows the rejection and emits a `ctx.log.warn`, so a successful publish stays recorded and a leaked tempdir on an ephemeral runner is treated as the cosmetic issue it is.
